# ADR-0004: サブドメイン設計の反映先をアプリ内の疑似 DNS ゾーンにする

- 日付: 2026-08-27（決定自体は 2026-08-26、要件 v0.1.5 で FR-13 を「反映まで」に拡張したとき）
- 状態: 採用
- 関連: `docs/requirements.md` §2.2 / §9.1（`dns_records`）/ §10.1 / FR-13、`docs/specs/subdomain-plan.md`、issue #16 / #36 / #70

## 背景

FR-13（サブドメイン設計支援）は当初「GitHub のリポジトリを解析して**設計書を出す**まで」だった。
これだと「AI が提案してくれた」で終わってしまい、ドメイン管理プラットフォームとしての
体験が閉じない。要件 v0.1.5 で「**反映まで**」に拡張したが、そこで
「何に反映するのか」を決める必要が出た。

前提として次の制約がある。

1. **本物の DNS 委任はできない。** 対象ドメインのネームサーバは疑似レジストリ
   （Kitaqsign / Kitaqnic）が管理しており、実インターネットの権威 DNS に委任されていない。
   NS を何に向けても名前解決はされない。
2. **外部 DNS プロバイダに反映するとデモが壊れやすい。** Cloudflare / Route 53 等に
   実際のレコードを作る形にすると、外部の資格情報・レート制限・課金・後片付けが
   ハッカソンの 4 日間に載ってくる。発表当日に外部サービスの不調で落ちるリスクも負う。
3. **要件 §2.2 は汎用 DNS ゾーン管理を非スコープにしている。** MX / TXT を含む
   任意レコードの編集はやらない。FR-13 が必要とするのは、リポジトリ解析から出てくる
   `api.` / `docs.` / `app.` のようなサブドメインを、`A` / `CNAME` / `ALIAS` で並べることだけ。

## 決定

**サブドメイン設計の反映先を、アプリ内だけで完結する「疑似 DNS ゾーン」（`dns_records` テーブル）にする。**
実インターネットには公開せず、外部 DNS プロバイダにも反映しない。

- 反映（`POST /domains/:name/subdomain-plan/apply`）は、保存済み設計と `dns_records` の
  **差分 upsert + 削除**。設計から消えたホストの行は削除する。反映前に差分
  （追加 / 変更 / 削除の件数と対象ホスト）を確認ダイアログで見せてから実行する。
- レコードの値域は `packages/shared/src/subdomains.ts` の `DNS_RECORD_TYPES`
  （`A` / `CNAME` / `ALIAS`）と `DNS_RECORD_SOURCES` が正。差分計算も同じファイルの
  `diffDnsRecords` が持つ（DB 側ではなく shared に置くのは、画面が反映前に同じ差分を
  出せるようにするため）。
- `UNIQUE(domain_id, host, record_type)` を張り、同じホストに同種のレコードは 1 件だけ持つ。
  差分 upsert の競合検出キーになる。
- `source` は現状 `subdomain_plan` のみ。将来の手動編集用に列だけ用意してある。
- **NS 切替は本物のレジストリ操作として行う。** 反映時にドメインのネームサーバが
  ドパ民 DNS（`DOPAMIN_NAMESERVERS` = `ns1/ns2.dopamin.ut42tech.com`）でなければ、
  FR-09 の `domain:update` で切り替える。**ここだけは疑似ではなく実レジストリに効く。**
  「設計をアプリ内に持ちつつ、レジストリ上の状態も辻褄が合っている」ことをデモで見せるため。

## 却下した案

### 外部 DNS プロバイダ（Cloudflare / Route 53）に実レコードを作る

「本物っぽさ」は最大だが、上の制約 1 により**そもそも名前解決されない**（レジストリが
実インターネットに委任していないので、外部プロバイダにゾーンを置いても引かれない）。
本物に見えて実は動かないものを作ることになり、外部資格情報・課金・後片付けのコストだけが残る。

### `domains.raw_info` などに JSON で持つ

テーブルを増やさずに済むが、差分 upsert のたびに JSON を読み書きすることになり、
`UNIQUE(domain_id, host, record_type)` に相当する制約を DB で表現できない。
ホスト単位の一覧・削除も SQL で書けなくなる。

### 反映を行わず設計書の出力までに留める（v0.1.4 まで）

体験が閉じない。「提案 → 保存 → 反映 → 反映済みバッジ」まで通してはじめて
ドメイン管理プラットフォームの機能に見える。デモシナリオ（§3.3 手順 5）の骨格でもある。

## 影響

- `packages/db` に `dns_records` を追加（`packages/db/drizzle/0008_odd_caretaker.sql`）。
  `domain_id` は `ON DELETE CASCADE` なので、ドメインを廃止・デモリセットすると一緒に消える。
- `subdomain_plans.applied_at` で「反映済みか」を持つ。画面の反映状態バッジはここを見る。
- 操作ログ（FR-15）には `subdomain_plan.apply` として記録する。**レジストリ通信を伴わない
  アプリ内操作**なので、`operation_logs.command` の語彙に主コマンド・補助コマンドとは別の
  カテゴリ（`APP_OPERATION_COMMANDS`）を作った（§9.1）。同じ反映処理の中で NS 切替が
  起きた場合、そのレジストリ呼び出しは従来どおり `update` として別行で記録される。
- **実インターネットの名前解決には一切関与しない**ことを §2.2 に明記した。デモや発表で
  「本物の DNS が引ける」と誤解させないこと。
- 将来、実インターネットに委任できる環境が手に入ったら、`dns_records` をそのまま
  ゾーンファイル相当として外部プロバイダへ流す拡張はできる（`source` 列と差分計算が
  すでにその形になっている）。ただし現時点ではスコープ外。
