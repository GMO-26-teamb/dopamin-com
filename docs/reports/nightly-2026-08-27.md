## 3. 設計上の判断（レビュー時に見てほしい点）

### 3.1 #67 は issue の想定と要件書が食い違っていた

issue #67 は「埋め込み → pgvector cosine → `uniqueness_checks` に 24h キャッシュ →
`POST /ai/uniqueness` → θ の較正」を求めているが、この設計は **ADR-0003 と
requirements v0.1.14（2026-08-26）で不採用**になっている。

- §10.1 のルート表に `POST /ai/uniqueness` は無い
- §9.1 で `reference_names` / `uniqueness_checks` は「不採用（ADR-0003）」と明記
- §13.3 の埋め込み、§17 の `EMBEDDING_*` / `UNIQUENESS_THETA_*` も不採用
- ラベル境界 40 / 70 は環境変数ではなく実装が固定で持つ（§14.2）

そのうえで、issue の実質的な中身は既に満たされていた（スコア算出は #28 / #155 の純粋関数、
`/domains/check` への組み込みは実装済み）。そこで **不採用の設計を実装するのではなく、
残っていた食い違いを潰す**方針にした。

- `lib/env.ts` / `.env.example` から `EMBEDDING_PROVIDER` / `EMBEDDING_MODEL` /
  `UNIQUENESS_THETA_LOW` / `UNIQUENESS_THETA_HIGH` を削除（§17 の表に無い）
- `packages/shared/src/uniqueness.ts` の doc から θ 較正の記述を削除
- AC-05-1（`google` / `amazon` / `youtube` が `low`）と AC-05-3（1 件 1.5 秒以内）を
  実コーパスで検証する回帰テストを追加（`packages/shared/src/uniqueness/latency.test.ts`）

**判断が違う場合はここだけ差し戻してください。**

### 3.2 `POST /ai/uniqueness` は作っていない

上記のとおり §10.1 に無いため。`routes/ai.ts` にその旨をコメントで残している。

### 3.3 GitHub 解析は実キー前提にしない（#68）

指示どおり `packages/registry` の mock と同じ思想にした。

- `GITHUB_MODE`（既定 `mock`）でネットワークに出ないフェイク応答へ切り替わる
- 失敗系は `GITHUB_MOCK_FAIL_MODE`（`not_found` / `rate_limited` / `unreachable`）で再現
- `GITHUB_TOKEN` は `real` でも任意（未設定なら未認証で叩く。レート制限の緩和用）
- **`docs/requirements.md` §17 に 2 行追記した**（環境変数の追加なので要件書を更新）

### 3.4 AI の structured output スキーマを厳しくしない（#66）

`generateObject` に渡すスキーマを `sldSchema` まで厳格にすると、1 件でも RFC 1035 違反が
混ざった瞬間に応答全体が捨てられ、正しい 5 件まで失う。
そのため AI の素の出力は「3 つの文字列」という形だけを保証し、値の妥当性は候補 1 件ずつ
`domainCandidateSchema` で再検証している（AC-04-1 の担保点はこちら）。

なお `reason` の 40 字上限は**表示上の制約**なので、超過は候補を捨てずに切り詰めている。

### 3.5 `subdomain_plan.apply` を操作ログの語彙に足した（#70）

FR-13 が「操作ログ（FR-15）に `subdomain_plan.apply` として記録」と名指ししているが、
これはレジストリ通信ではない。既存の `OPERATION_COMMANDS`（主 15 種 + 補助 5 種）は
レジストリ通信の語彙なので、`APP_OPERATION_COMMANDS` という別カテゴリを追加し、
`<機能>.<操作>` 表記でレジストリコマンド（snake_case）と見分けられるようにした。
`operation-log.test.ts` の「すべて snake_case」テストは、レジストリ通信のコマンドに対する
検証へ書き換えている。

### 3.6 デモ投入は mock 固定（#71）

【要確認 §21.2 #7】が未解決なので実レジストリへの実登録は行っていない。
`REGISTRY_MODE=real` の環境では `OPERATION_NOT_ALLOWED`（409）で**明示的に拒否**する
（黙って実レジストリに `dopamin-demo-*` を登録する方が危ないため）。

`packages/registry` の mock に `seedOwnedDomain` を追加した。`create` は「今つくったドメイン」
しか作れず、FR-16 が要求する「期限間近」「RGP 中」という途中の状態を再現できないため。

指示書は `packages/db/src/seed/demo.ts` の `seedDemoData(db, userId, { mock })` を求めていたが、
**投入の choreography は `apps/api/src/services/demo.service.ts` に置いた**。
`packages/db` から `packages/registry` を参照すると層が逆転すること、
行の写像（`toDomainValues`）と移管の記録（`recordInboundTransferRequest` /
`recordOutboundTransferRequest`）を二重に持つことになるため。
`packages/db/src/seed/demo.ts` は命名・シナリオ定義・削除（`clearDemoData`）を持つ。
