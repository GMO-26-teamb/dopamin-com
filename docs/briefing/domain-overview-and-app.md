## 02. ドメイン基礎知識 — Domain Fundamentals

### 2.1 IPアドレスとドメイン

Webサイトを開く・メールを送信するには、インターネットを通じてどのサーバーにアクセスするか特定する必要がある。

```
ユーザー                    →  DNSサーバー              →  Webサーバー
www.onamae.com と検索          ドメイン名 → IPアドレスを応答   210.172.128.200
（人間がわかりやすい文字列＝ドメイン）  （DNS変換）                （IPアドレス＝住所情報）
```

- **DNS（Domain Name System）**: ドメイン名とIPアドレスを紐づけて変換する仕組み。インターネットの「電話帳」のような役割。
- **DNS階層構造**: ルートDNS（`.`）→ TLD DNS（`.com` 等）→ 権威DNS

> **POINT** IPアドレスは覚えにくいため、人間が扱いやすい文字列（ドメイン）に変換する仕組みがDNS。

### 2.2 ネームサーバーと委任

名前解決は、上位ゾーンから順に「どの権威DNSが担当か」を辿る＝**委任（Delegation）** の連鎖。

```
ルートDNS（.）      →  上位DNS（.com）  →  権威DNS                    →  Web／メールサーバー
                       「.com」の一覧を管理   ns1/ns2.onamae.ne.jp          IPを返答
                                              ゾーン（A/MX/TXT等）を保持
```

**委任（Delegation）の要点**

- 委任＝上位ゾーンが「下位ドメインの権威DNSはどれか」を指し示すこと
- ドメイン登録時にNS（例: `ns1.onamae.ne.jp`）を上位DNS側へ登録 → 上位ゾーンに委任情報（NSレコード）が載る
- お名前.comはレンタルDNSとして権威DNSを提供。NSを変更すると使用する権威DNS（ゾーン）が切り替わる

> **POINT** 権威DNSが保持する「DNSレコードの種類」は次項（2.3）を参照。

### 2.3 DNSレコードの種類

権威DNS（ゾーンファイル）に登録される設定情報。お名前.comのレンタルDNSでは管理画面から設定できる。

| レコード | 役割 | 例 |
|---|---|---|
| A | ホスト名 → IPv4アドレス | `example.com` → `210.172.128.200` |
| AAAA | ホスト名 → IPv6アドレス | `example.com` → `2001:db8::1` |
| CNAME | 別名（エイリアス） | `www` → `example.com` |
| MX | メール配送先サーバー | `mail.example.com`（優先度10） |
| NS | 権威ネームサーバーの指定 | `ns1.onamae.ne.jp` |
| TXT | 任意の文字列（SPF／DKIM等の認証） | `"v=spf1 include:..."` |

> **POINT** ホスト名→IP（A/AAAA）、別名（CNAME）、メール配送（MX）、権威DNS指定（NS）、認証用文字列（TXT）が代表例。

### 2.4 TLD（トップレベルドメイン）

ドメイン名をドットで分割した際の最後の部分。例: `www.gmo.jp` → `.jp` がTLD。2026年時点で約1,400種類以上（IANA Root Zone Database調べ）。

| 種別 | 数 | 説明 | 例 | 備考 |
|---|---|---|---|---|
| gTLD（分野別） | 1,200個以上 | 用途・分野別のTLD | `.com`, `.net`, `.org` 等 | ICANNが仕様を統一 |
| ccTLD（国別） | 約250個 | 国・地域を表すTLD | `.jp`, `.uk`, `.us` 等 | 国ごとに仕様が異なる |
| sTLD | 約14個 | 特定組織向け | `.gov`, `.edu` 等 | |
| インフラTLD | 1個 | インフラ用 | `.arpa` のみ | |

> **POINT** 登録対象はSLD+TLD（例: `example.co.jp`）。サブドメインは登録者がDNSで自由に追加できる。ICANNは2012年以降、sTLDとgTLDの区別を廃止しgTLDに統一。

### 2.5 gTLDの歴史

| 時期 | 状況 | 内容 |
|---|---|---|
| 1984〜88 | 7種類のみ | com / net / org / edu / gov / int / mil |
| 2000 | 7種類追加 | biz / info / name 等 |
| 2012 | 新gTLDプログラムで自由化 | `.shop` `.tokyo` 等 |
| 現在 | 1,200種類以上 | |

> **POINT** 2012年の新gTLDプログラム（自由化）以降gTLDは急増。用途特化型（`.shop` / `.app` 等）や地域型（`.tokyo` 等）など、多様化が進んでいる。

## 03. ドメイン業界構造 — Industry Structure

### 3.1 ドメインの商流とプレイヤーの役割

| プレイヤー | 役割 |
|---|---|
| **IANA** | 技術的資源管理（IP割当・ルートゾーン・TLDの技術管理）。ICANN内の一部門 |
| ▼ **ICANN** | 国際管理団体（1998年設立）。レジストラ認定・gTLD承認・ポリシー策定・IANA監督 |
| ▼ **レジストリ** | TLDごとの管理団体（卸）。ゾーン管理・配信、ユーザーへ直販不可。例: Verisign / JPRS / GMOドメインレジストリ |
| ▼ **レジストラ** | ICANN認定の直販事業者。レジストリと仕入交渉し1円提供も。**← お名前.comはここ** |
| ▼ **リセラー** | レジストラから仕入れて再販する代理店 |
| ▼ **エンドユーザー** | ドメインの利用者 |

### 3.2 レジストラの機能

レジストラが持つ主要機能 — 各操作はレジストリへのEPPコマンドで実行される（→ 4.2 EPP概要）。

| 機能 | EPPコマンド | 説明 |
|---|---|---|
| 登録 | Create | 新規ドメイン登録 |
| 更新 | Renew | 有効期限の延長 |
| 情報変更 | Update | NS、コンタクト等の変更 |
| 廃止 | Delete | ドメインの削除 |
| 移管 | Transfer | 他レジストラへの移動 |
| 情報取得 | Info | ドメイン詳細取得 |
| 存在確認 | Check | 登録可否確認 |

### 3.3 ドメイン移管（レジストラ間の移行）

```
              レジストリ（1つ）
   TLDごとの登録台帳。両レジストラは同じ1つのレジストリに接続
        ▲                          ▲
レジストラA（移管元・他社）  →  レジストラB（移管先・お名前.com）
   移管OUT（Transfer OUT）        移管IN（Transfer IN）
        AuthCodeで本人確認のうえ移管
```

**ユーザーが移管する動機**

| # | 動機 | 説明 |
|---|---|---|
| ① | UI（管理画面）の使いやすさ | 直感的で分かりやすい管理画面を求めて、移管を検討するユーザーもいる |
| ② | 更新料金の安さ | 他社より安価な更新料金を求めて移管。ドメインは毎年更新が必要なため、更新料金の差は移管の大きな動機になる |

> **POINT** レジストリは1つ: 移管してもドメインを管理する台帳は変わらない。切り替わるのは取り次ぐレジストラのみ。ICANN規定により、**登録・前回移管から60日間は移管不可**。

## 04. ドメインのライフサイクルとEPP — Domain Lifecycle

### 4.1 ドメインの状態遷移

**Grace Period（猶予期間）** ＝ ICANNが定めたドメイン操作を取り消し可能な期間（RFC 3915）。

```
登録可能 → Create → 登録済み（Active） → 期限切れ（Expired） → Grace Period → 登録可能
                                          AGP/Renew GP/Transfer GP 等   削除・再登録可能
```

| Grace Period | 期間 | 返金／措置 | 説明 |
|---|---|---|---|
| Add GP（AGP） | 5日 | あり（無課金） | 登録直後の取消可能期間 |
| Renew GP | 5日 | あり | 更新直後の取消可能期間 |
| Transfer GP | 5日 | あり | 移管直後の取消可能期間 |
| Auto-Renew GP | 30-45日 | あり | 自動更新 → Restoreで復帰 |
| Redemption GP（RGP） | 30日 | 復旧費用 | 未復旧ならPending Deleteへ |
| Pending Delete | 5日 | 不可 | 操作不可。期限後は削除・再登録可能 |

> **POINT** Grace Periodの長さはTLDごとに異なる。RGPからの復旧（restore）は追加費用が発生する。

### 4.2 EPP概要と主要コマンド

**EPP（Extensible Provisioning Protocol）** — レジストラとレジストリ間の標準通信プロトコル。

- 規格: RFC 5730（基本仕様）
- 形式: XML
- 通信: TCP（ポート700）＋TLS

| コマンド | 用途 |
|---|---|
| login / logout | セッション管理 |
| check | ドメインの登録可否確認 |
| info | ドメイン詳細情報取得 |
| create | 新規登録 |
| renew | 更新（期間延長） |
| update | 情報変更（NS、コンタクト等） |
| delete | 削除 |
| transfer | 移管 |
| poll | レジストリからの通知取得 |

```
レジストラ  --- EPP / XML over TLS ポート700 --->  レジストリ（Verisign 等）
```

> **本ハッカソンでの注意点**
> 本物のEPPは、TCP接続管理・XML名前空間・TLSクライアント認証といった要素の学習コストが大きく、本来学んでほしい「ドメイン管理ロジック」や「複数レジストリの差分吸収」に集中しづらくなる。そのため、**本ハッカソンではトランスポートを扱い慣れた HTTP/REST + JSON とする**。

### 4.3 EPPステータスコード

ドメインの状態を示すコード — Client（レジストラ設定）とServer（レジストリ設定）の2種類がある。

| ステータス | 意味 | 備考 |
|---|---|---|
| `ok` | 正常状態 | 他のステータスがない場合のみ |
| `inactive` | ネームサーバー未設定 | ゾーンファイルに含まれない |
| `clientHold` / `serverHold` | DNS解決停止 | ゾーンファイルから除外 |
| `clientTransferProhibited` / `serverTransferProhibited` | 移管禁止 | ― |
| `clientDeleteProhibited` / `serverDeleteProhibited` | 削除禁止 | ― |
| `clientUpdateProhibited` / `serverUpdateProhibited` | 更新禁止 | ― |
| `redemptionPeriod` | RGP中 | 復旧可能 |
| `pendingDelete` | 削除待ち | 操作不可 |

> **POINT** ServerステータスはClientステータスより優先される。

### 4.4 ドメイン登録のE2Eフロー（申込〜DNS反映）

ユーザーの申込からDNSで名前解決できるまでの全体像。レジストラはEPPでレジストリと連携する。

| ① ユーザー | ② レジストラ | ③ レジストリ | ④ 権威DNS | ⑤ 名前解決 |
|---|---|---|---|---|
| レジストラでドメインを検索・申込 | 空き確認(check) → 登録(create) → NS設定(update) | 台帳へ登録、ゾーンファイルに反映 | 世界中のDNSへゾーン情報を配信 | キャッシュ反映後アクセス可能に |

> **POINT** ②③の連携はEPPコマンド（check / create / update）で行われる（→ 4.2）。反映時間はレジストリ処理＋DNSのTTL／キャッシュに依存し、登録直後はアクセスできないことがある。
> ドメインの「状態」（Active等）はEPPで管理され、ライフサイクル（4.1）と対応する。

## 05. 登録データとプライバシー — Registration Data & Privacy

### 5.1 RDDS / Whois / RDAP

**RDDS（Registration Data Directory Services）** ＝ ドメイン登録データを検索・参照するサービスの総称。Whois（従来）とRDAP（現行標準・2025年1月以降）がある。

| 項目 | Whois（従来方式） | RDAP（現行標準） |
|---|---|---|
| プロトコル | ポート43／TCP | HTTPS |
| データ形式 | 非標準テキスト | JSON（RFC 9083） |
| 認証・認可 | なし | 対応可能 |
| 国際化 | 限定的 | Unicode対応 |

- **Whois情報公開代行**: 登録者情報を代理公開しプライバシー保護（現在はPolicyにより原則リダクション → 5.2）
- **RDDSで参照できる主なデータ**: ドメイン名・登録者・NS・登録／有効期限・ステータス（コンタクト詳細 → 5.2）

### 5.2 コンタクト情報と登録データの公開

従来の「基本4コンタクト」は、ICANNの **Registration Data Policy（2025年8月21日発効）** により収集要件が必須・任意・撤廃へ再整理された。

| コンタクト種別 | 役割 | 改定後 |
|---|---|---|
| Registrant（登録者） | 正式な保有者。権利の帰属先 | **必須** |
| Technical（技術） | DNS等の連絡窓口 | 任意 |
| Administrative（管理） | 管理・運用上の連絡窓口 | 撤廃 |
| Billing（請求） | 請求・支払い窓口 | 撤廃 |

**登録データの公開ポリシー**

- Registrant: 必須（正確性・変更時7日以内の更新義務）
- Technical: 任意（提供義務なし／登録者本人と同一指定も可）
- Administrative・Billing: 撤廃（収集・公開等の要件を廃止）
- 登録データは原則非公開（リダクション）
- 適用データセット（最小／フル）はTLD・法的根拠で異なる
- Organization入力時はその組織が法的所有者
- 背景: GDPR等の個人データ保護（データ最小化）

> ※学習容易性のため、kitaqsign／kitaqnicとも **thick実装**（`domain:create` で registrant/contacts を指定、レジストリが保持・RDAPでも返却）。実運用のRDPに基づく最小化・redactionは簡略化（両レジストリでコンタクト操作を学べるため）。**PII（氏名・メール等の個人情報）は許可ダミー値のみ使用**。

出典: ICANN Registration Data Policy（2025年8月21日発効）

## 07. システム概要 — System Overview

### 7.1 システム構成

```
NAVI（画面）
    │
   API ──────┬──── BRIDGE ────→ REGISTRY
    │        │                   Verisign / JPRS / GMO REGISTRY
   BATCH ────┘                   Key-Systems / GoDaddy Registry
    │                            Identity Digital / CentralNic 他
   DB
（バックエンド）
```

**なぜレイヤーを分けるのか**

- **画面／API**: メンテナンス等でAPIが一時的に使えなくても画面（Webページ）は表示を継続でき、PC・スマホなど複数プラットフォームでの開発も進めやすくなる
- **API／BRIDGE**: レジストリごとに通信仕様が異なるため、その違いをBRIDGE層に閉じ込め、APIからは意識せずに済むようにしている

## 08. 開発するアプリ概要 — Application Overview

### 8.1 アプリコンセプト

ICANN認定レジストラと同様に、会員向けにドメインのライフサイクル操作を提供する **「疑似レジストラサービス」** を開発する。

```
会員          →  開発するアプリ   →  EPP                        →  Kitaqsign / Kitaqnic
エンドユーザー     疑似レジストラ      check / create / update /     疑似レジストリ
                                   renew / delete / transfer /
                                   restore
```

**本アプリの役割**: 会員が保有するドメインの登録・更新・情報修正・廃止・復旧・移管を、Kitaqsign / Kitaqnic の疑似レジストリに対するEPPコマンドとして実行する。

> **POINT** 実際のレジストラ／レジストリと同じ関係性（レジストラ＝会員接点、レジストリ＝台帳管理）を疑似環境で再現します。EPPの仕様理解が実装の土台になります（→ 11.1 参考資料）。

### 8.2 レジストリ構成とAPI仕様

| 疑似レジストリ | 役割 | APIドキュメント（Swagger UI） |
|---|---|---|
| Kitaqsign | 疑似レジストリ①。ドメインのライフサイクル操作をEPP形式のREST APIで提供 | https://docs.kitaqsign.com/swagger-ui/index.html |
| Kitaqnic | 疑似レジストリ②。Kitaqsignと並行して連携する2つ目の疑似レジストリ | https://docs.kitaqnic.com/swagger-ui/index.html |

**開発時の注意点**

- 2つのレジストリはAPIの提供形式（EPPコマンド相当のREST API）が異なる場合があるため、実装前に**両方のSwagger UI**でリクエスト／レスポンス形式・認証方式・エンドポイントを確認すること
- 実際のEPP（RFC 5730）と対応関係にあるが、疑似実装のため**両ドキュメントの仕様を正とする**
- アクセス制限がある場合は運営に確認すること

## 09. 必須機能（コア機能） — Core Features

### 9.1 会員向け必須機能

すべての機能は Kitaqsign / Kitaqnic へのEPP相当コマンドとして実行される。

| 機能 | 対応EPPコマンド（想定） | 概要 |
|---|---|---|
| 登録 | check → create | 希望ドメインの空き確認のうえ、新規登録を行う |
| 更新 | renew | ドメインの有効期限を延長する |
| 情報修正 | update | ネームサーバーやコンタクト情報等を変更する |
| 廃止 | delete | 会員の申請によりドメインを削除する |
| 復旧 | restore（RGP経由） | 削除後の猶予期間（RGP）内にドメインを復旧する |
| 移管 | transfer | 他レジストラ（本アプリ含む）との間でドメインを移管する（IN／OUT） |
| 情報参照 | info | 会員が保有するドメインの詳細情報を取得・一覧表示する |

> ※実際のコマンド名・パラメータは各レジストリのSwagger仕様に従うこと（→ 8.2）。

### 9.2 機能フロー例（ドメイン登録）

会員の申込から登録完了までの一連の流れ。他の機能（廃止・移管等）も同様に「会員操作 → アプリ → EPPコマンド」で実現する。

| ① ドメイン検索 | ② 登録申込 | ③ NS設定 | ④ 登録完了 |
|---|---|---|---|
| 会員が希望のドメイン文字列を入力 | 空きを確認し、登録内容（期間・NS等）を入力 | 初期ネームサーバー等の情報を設定 | 会員の管理画面に反映され利用可能に |
| `check` | `create` | `update` | `info` |

> **POINT** 廃止（delete）・復旧（restore）・移管（transfer）についても、EPPのステータス・猶予期間（Grace Period）を意識した実装が求められる。第4章「ライフサイクルとEPP」を復習すると設計しやすい。
