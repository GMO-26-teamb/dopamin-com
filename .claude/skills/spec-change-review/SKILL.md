# 仕様変更レビュー

`docs/requirements.md` は要件の SSOT。レビュー対象に requirements.md の差分が含まれる場合、
それは**コードの良し悪しより先に「その仕様変更が正しいか」を人間が決めるべき変更**。
レビューの最初にここを確認する。

## 1. レビュー対象の差分を取る

依頼の形に応じて範囲を決める:

```bash
# 未コミットの変更をレビューする場合
git diff HEAD -- docs/requirements.md

# ブランチ全体をレビューする場合（main との差分）
git diff main...HEAD --stat -- docs/ && git diff main...HEAD -- docs/requirements.md

# GitHub PR をレビューする場合
gh pr diff <PR番号> -- docs/requirements.md
```

`docs/specs/*.md` と `docs/adr/*.md` の差分も同時に見る（要件変更は spec / ADR を伴うことが多い）。

## 2. 差分がない場合

要件変更なしとして通常のレビューに進む。ただし**逆方向のチェック**を 1 回だけ行う:

- コード差分に、requirements.md に書かれていない挙動・エンドポイント・テーブル・AC が入っていないか
- 入っていれば「要件未反映の実装」としてレビュー指摘に含め、requirements.md を更新すべきかユーザーに問う（`spec-change-guard` と同じ確認）

## 3. 差分がある場合 — ユーザーに問う

**先に差分を要約して見せてから**質問する。要約は次の表形式:

| 要件ID | 種別 | 変更内容（before → after） | 影響範囲 |
|---|---|---|---|
| FR-06 | 変更 | AC に「登録前に確認ダイアログ」を追加 | `apps/web` 登録導線、E2E |
| FR-19 | 追加 | 新規要件（P1） | 未実装 |
| NFR-03 | 削除 | 非スコープへ移動 | 既存テストの削除要否 |

そのうえで `AskUserQuestion` で問う:

> この PR には `docs/requirements.md` の仕様変更が含まれています。上記の変更は意図どおり・合意済みでしょうか？

選択肢:

1. **意図どおり（承認済み）** — 仕様変更を前提にレビューを続行
2. **一部だけ意図どおり** — どの項目が意図と違うかを聞き、その差分の取り消し案を出す
3. **意図と違う（要件は変えないはず）** — requirements.md の差分を戻す提案を出し、コード側が要件に沿っているかを再チェック
4. **判断保留** — レビューをブロックし、未確認事項として明示して終える（承認判定は出さない）

## 4. 版（バージョン）が更新されているかを必ず確認する

`docs/requirements.md` に差分がある以上、**版番号と更新履歴の更新は必須**。忘れられやすいので機械的に確認する。

```bash
# 1) 冒頭の表の「版」
grep -n '^| 版 |' docs/requirements.md

# 2) 更新履歴の最新行
sed -n '/^### 更新履歴/,$p' docs/requirements.md | tail -3

# 3) 変更前（main / HEAD）の版と比較する
git show main:docs/requirements.md | grep '^| 版 |'          # ブランチ・PR レビュー時
git show HEAD:docs/requirements.md | grep '^| 版 |'          # 未コミット変更のレビュー時

# 4) 差分に版と更新履歴が含まれているか
git diff main...HEAD -- docs/requirements.md | grep -E '^[+-].*(\| 版 \||^\+\| v[0-9])'
```

判定基準:

- [ ] **版が上がっている** — 変更前より新しい版になっている（例 `v0.1.1` → `v0.1.2`）。据え置きは NG
- [ ] **上げ幅が変更規模に合っている** — 文言整理・追随更新はパッチ（`v0.1.1` → `v0.1.2`）、要件の追加・削除・スコープ変更はマイナー以上（`v0.1.x` → `v0.2`）
- [ ] **冒頭の表の `版` と `### 更新履歴` の最新行の版が一致している** — 片方だけ更新されていることが多い
- [ ] **更新履歴に行が 1 行追加されている** — `| 版 | 日付 | 内容 |` の 3 列が埋まっている
- [ ] **日付が正しい** — 変更を入れた日付。過去の版の日付をコピーしていない
- [ ] **内容欄が具体的** — 「更新」「修正」だけは NG。変更した要件 ID（`FR-06` 等）と、判断が伴う場合は ADR 番号（`ADR-0001`）を含める
- [ ] **既存の履歴行が書き換えられていない** — 過去の行の改変・削除は差し戻し対象

いずれかを満たさない場合は、**レビュー指摘として明示し、修正案（追加すべき更新履歴の行と版番号）をそのまま提示する**。

提示例:

> `docs/requirements.md` の版が `v0.1.1` のままです。以下を追加してください。
>
> | 版 | 日付 | 内容 |
> |---|---|---|
> | v0.1.2 | 2026-08-25 | FR-06 に登録前確認ダイアログの AC を追加。FR-19（サブドメイン一括作成）を新規追加 |
>
> あわせて冒頭の表の `版` も `v0.1.2（2026-08-25）` に更新。

## 5. その他のチェックリスト

版の確認（§4）に加えて、変更の**体裁**を機械的に確認して指摘する:

- [ ] 要件 ID が既存と衝突していない / 既存 ID の意味を変えていない
- [ ] 変更した要件に対応する `docs/specs/<feature>.md` が更新されている（未作成なら未着手であることが明示されている）
- [ ] 解消された `【要確認】` が本文と `§21.2 未決事項` の両方から消えている
- [ ] 新規・変更要件に優先度（P0/P1/P2）が付いている
- [ ] スコープ（`§2`）・データモデル（`§9`）・API 設計（`§10`）との矛盾がない
- [ ] 大きな設計判断を伴う場合 `docs/adr/` に ADR がある
- [ ] コード差分が要件差分と整合している（片方だけ変わっていない）
- [ ] 変更した AC に対応するテストがある（`pnpm check` がグリーン）

## 6. レビュー結果の出し方

レビューコメント／サマリの**先頭に仕様変更セクションを置く**:

```
## 仕様変更（docs/requirements.md）
- 確認結果: 意図どおり（ユーザー確認済み）/ 未確認 / 差し戻し
- 版: v0.1.1 → v0.1.2（更新履歴あり）/ ★未更新（要修正）
- 変更要件: FR-06（変更）, FR-19（追加）
- 追随の要否: docs/specs/domain-register.md 更新済み / ADR 不要
```

- 未確認のまま「LGTM」やマージ推奨を出さない
- 版が未更新のままマージ可としない（要件差分があるのに版据え置きは必ず指摘する）
- 仕様変更が意図と違うと判明した場合は、コード側の指摘より先にその取り消しを提案する
